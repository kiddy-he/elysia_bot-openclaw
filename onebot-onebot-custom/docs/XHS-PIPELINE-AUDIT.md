# 小红书搜索媒体链路审计（2026-10-21）

最新复测见 [2026-10-22 分段计时报告](XHS-PIPELINE-TIMING-20261022.md)，包含真实 QQ 回执、后台任务耗时及正常分类后遇到 461 的独立样本。本文以下时间仍保留为 2026-10-21 历史数据。

## 现行链路

1. QQ 入站消息进入 OneBot，先由先验分类模型判断是否为小红书业务。
2. 主模型将自然语言转成 `xhs_search_posts` 参数；当前示例“点赞数比较高的爱莉西雅coser图片”被转成 `query: 爱莉希雅 cos`、`media_type: image`、`limit: 12`。
3. XHS 执行器对查询做基础规范化：去首尾空白、去前导 `#`，补默认 `limit=6`、`sort=relevance`、`search_mode=keyword`，并按请求上下文缓存完全相同的查询。
4. 搜索结果在当前候选范围内按点赞数比较；inspect 重新核对帖子详情，再列出每帖图片。
5. `download_images` 根据图片句柄识别帖子并自动扩展为完整图集；后台任务下载、校验、哈希和保存全部图片。
6. `job_status` 等待任务完成；`read_artifact` 校验产物并暂存该帖完整图集。
7. `xhs_send_media` 按帖子分组，创建一个合并消息；每个节点为 `【帖子标题】` 文本段后接该帖全部图片（视频帖为标题后接视频）。
8. QQ 合并 API 返回真实 `message_id` 后才确认送达；总结文字通过普通文本消息单独发送。

## 搜索词与重复请求

搜索词有基础清理和默认参数处理，但当前没有独立的搜索词改写模型、同义词扩展或语义相似度改写。搜索排序只支持 `relevance`/`latest`；“高赞”是在本次搜索候选中按点赞数排序，不能解释为全站最高赞。

缓存键包含请求上下文和完整规范化参数，因此同一请求内完全相同的搜索会命中缓存。投递队列对同一入站请求使用 dedupe，重复调用不会再次发 QQ 合并消息。不同入站请求即使文本相同或相似，目前不会跨请求自动排除已发送帖子，也不会保证选择不同内容；是否换帖取决于主模型的上下文判断。后续若要避免短时间重复，应增加按收件人、查询规范化键和时间窗保存最近已发送 `post_id`，并在候选选择阶段显式排除；需保留用户明确指定帖子优先级。
