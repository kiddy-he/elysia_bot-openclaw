# XHS SMS recovery

The shared XHS account uses the tested `/root/komachi-xhs-js/src/backends/sms-login.js` implementation documented in that project's `docs/SMS-LOGIN.md`. This is an operator workflow; no new model tools or login parameters are exposed. `onebot-xhs.json` enables it with `smsRecovery.enabled: true`. The browser verification workflow remains the fallback when SMS recovery is disabled.

A single explicit `login_required` result triggers one flow immediately, including nested inspect/job errors and an already stopped request carrying that same login terminal. Alternatively, two distinct real upstream HTTP 461 failures within 15 minutes trigger one flow. Cached/local challenge request-stop failures do not count toward the 461 threshold. `session_invalid`, permission errors and rate limits do not request SMS. The first phone prompt distinguishes expired login from repeated challenges. A successful content read resets the consecutive counter. The coordinator pauses at most 16 original tasks for at most 30 minutes. One flow is allowed per hour, with ten minutes to reply. The first flow asks the configured default account's private admins for the existing account's mainland phone number if `/root/.openclaw/secrets/xhs-phone.json` is absent. Later flows reuse it. This file and the durable coordinator state have mode 0600. No phone is embedded in public configuration.

SMS send and completion reuse the standalone module, account lock and pending identity. Before formal session commit, enabled configuration and admin grants are checked again. Phone and six-digit OTP are accepted only from the actual private admin recipient quoting the corresponding default-account request receipt. `gateway.bufferMessage` intercepts them before debug logging, classification or history. Code values are never persisted. Invalid/expired/unauthorized replies to known authentication prompts are consumed. Requests are not automatically resent; challenge/rate-limit failures stop the flow. The underlying library preserves existing formal credentials until explicit non-guest verification succeeds.

After authentication, queued continuations recheck the original peer's grants, wait for the original dispatch, and resume only XHS tools. `prepareXhsResume` clears only that owner's explicit `challenge_required`/`login_required` terminals and failed read/download results. Successful reads and jobs, partial downloads, cancellations, uncertain operations, forward batch sealing and delivery dedupe survive. Original request IDs and resource handles remain valid. A second challenge stops rather than starting another login. Session reset cancels pending continuations. Startup resumes waiting-code state, but never blindly replays interrupted SMS sends, OTP checks, or dispatches whose send outcome could be uncertain.

Files: `features/xhs-sms-recovery.js` (state machine), `features/xhs-sms.js` (production adapter), `features/xhs-resume.js` (scoped recovery), `features/xhs.js` (errors), `gateway.js` (private interception and continuation). State: `state/business/xhs-sms-recovery.json`; authentication material remains in the existing XHS data directory. The production adapter refuses live automation under isolated `ONEBOT_CONFIG_ROOT` roots.

Validation uses fake SMS/upstream/QQ responses and real isolated SQLite stores; it does not request a live SMS. A real end-to-end acceptance still requires a genuine `login_required` or repeated-461 trigger, receipt of the account's SMS, an admin quoted reply, and successful recovered content/delivery receipts. A login success alone is not business-interface acceptance.

Tests cover the private phone/OTP flow, nested failures, deduplication, cooldown, rejected non-auth errors, and continuation without replaying completed/forbidden/different-owner work.
