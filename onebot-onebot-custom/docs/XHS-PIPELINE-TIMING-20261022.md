# XHS 消息入站、搜索、下载及发送耗时复测

测试日期：2026-10-22，Asia/Shanghai。单位为秒；`+` 表示相对测试消息注入时间，执行耗时不包括其前后的模型等待。

结论：当前主要瓶颈是模型多轮编排及运行时开销，其次是最终文字的审查、重复人设改写。成功样本下载 9 张图片只花 3.910 秒，QQ 合并发送花 9.712 秒；图片却到 +121.317 秒才收到真实发送回执，最终文字到 +174.736 秒。应优先减少无须模型决策的工具往返，并消除已通过审查的文字再次改写。

## 测试方法与边界

- 消息：`在小红书上找一些点赞数比较高的爱莉西雅coser图片发我`。
- 使用独立验收网关和工作区，向 OneBot 注入管理员私聊消息；LLM、小红书 API、CDN 下载和 QQ 私聊发送均为真实调用。仅向 admin 私聊发送。
- 网关就绪前的启动耗时不计入；消息注入后仍有约 0.5 秒连接/入站准备开销。工作区、模型会话为冷启动，并非生产常驻会话的平均耗时。
- 主模型 `antigravity/gemini-3.8-flash-high`，主链思考 high；入站分类与文字审查 `antigravity/gemini-3.5-flash-lite`；出站人设改写仍调用 Gemini high 模型，思考 off。
- 通过可选 preload 采集模型完整响应流、XHS 服务和执行器等待，结合操作数据库、后台下载任务完成事件、QQ 实际回执进行交叉核对。模型完整响应流耗时包含上游等待和响应传输，不等同于纯推理时间。
- 下载任务可被共享数据目录中的生产 worker 领取，所以实际下载用时取持久化 `jobs.created → job_finished`，没有将下载工具的“已排队”返回时间当作下载耗时。
- 两个样本不是统计平均值，不提供 p95 或吞吐结论。本次没有重测视频、大图集、群聊或多用户并发。
- 第二次遇到 461 后未继续调用小红书。隔离验收不会启动生产 SMS 自动恢复流程，因此本次不评价短信登录恢复的耗时或成败。

11 次前台工具全部完成，FIFO 等待均为 0 毫秒；本样本未出现并发繁忙或 `list_images` 重试。不过本次模型依次调用 3 次 `list_images`，不能据此推断高并发等待性能。

### 时间具体消耗在哪里

主模型共 **12 轮**请求，对应 11 次工具调用及最终回复生成，完整响应流累计 **83.415 秒**。其中图片发送之前 11 轮累计 **72.466 秒**。此外还有每轮工具结果入模、运行时调度、凭据读取等开销，不能把所有相邻步骤的空档都算成模型推理。

可以看到，3 次 `list_images` 执行累计仅 **13 毫秒**，但其开始时间从 +44.475 延伸到 +60.240；3 次 `read_artifact` 执行累计仅 **23 毫秒**，开始时间从 +91.513 延伸到 +103.547。让模型逐个决定这些确定性步骤，成本远大于工具执行本身。

下载在 +79.003 已完成，QQ 合并请求到 +111.605 才开始，中间还有 **32.602 秒**。主要是状态查询、逐帖暂存和发送之间反复调用模型。

图片发送后还需 **53.419 秒**才发完文字：

| 图片回执之后的阶段 | 时间范围 | 阶段耗时 | 其中模型网络耗时 |
|---|---|---:|---:|
| 回到主模型、生成最终回复 | +121.317 → +133.457 | 12.140 | 10.949 |
| 文字审查及调用准备/返回处理 | +133.457 → +147.323 | 13.866 | 2.511 |
| 出站处理、再次人设改写及文字发送 | +147.323 → +174.736 | **27.413** | **17.410** |

审查已经判定原回复语气贴合角色、可以发送，但普通 XHS 最终回复仍按默认规则再经 `rewriteForPersona`。两次额外模型调用都通过新的 `openclaw agent` CLI 会话执行，因而还包含进程与 agent 初始化等开销。网关记录 `deliver(final)` 是 +147.325，实际文字请求开始是 +174.261；这个日志并不代表 QQ 已经送达。

从详情工具结束（+31.020）到失败文字送达，间隔 **61.007 秒**。业务上确实被站点验证挡住，同时错误通知也被过长的生成、审查、改写链拖慢。

`xhs_inspect_posts` 的操作库状态仍为 `succeeded`，表示工具返回被正常处理；嵌套的 `data.resources` 有 `challenge_required`，因此不是全部帖子检查成功。类似地，验收脚本 `finished=true` 仅表示最终文字发送完成，本样本的业务结果是 **challenge_required，而非媒体发送成功**。

## 优化顺序与验收建议

### 1. 将确定性后半程改为宿主受控批处理（最高优先级）

保留模型理解需求、改写搜索词、选择帖子；选帖后由宿主执行：逐帖列图 → 全图集下载 → 等待任务 → 逐帖校验/暂存 → 单次合并发送。避免每个 `list_images`、`read_artifact`、`job_status` 都需要模型再次规划。

可先提供批量列图、批量暂存入口，或一个受控的“按已选帖子下载并发送”工具。前者可将 3 次列图和 3 次暂存合为 2 轮，按本次往返估计可减少 **20–45 秒**；进一步将常规流程由 12 轮主模型调用降至约 3–4 轮，空间更大。以上为当前轨迹推算，**不是优化后的实测数据，也不能简单相加**。

保留现有请求归属、权限重检、取消、预算、完整图集、每帖标题分组、投递去重和真实回执要求。遇到详情部分失败应由宿主立即短路，而不是把步骤自由交给模型继续尝试。

### 2. 已通过审查的最终回复直接投递（最高优先级）

对已经由主模型按角色生成、并通过文字审查的回复，传递明确的“已渲染/已审查”状态，跳过第二次人设改写；或者将审查与必要的改写合并为一次受控调用。仍保留角色、隐私和事实一致性检查。

本样本审查后到文字发送共 27.413 秒，其中 QQ 本身仅 0.475 秒，因此这部分约 **20–27 秒**有明显优化空间。另可复用常驻调用路径，减少审查/改写每次启动 CLI 与新 agent 会话的开销；需保留 helper 的工具禁用和上下文隔离。

### 3. 为 461 等明确失败建立短路径（高优先级）

结构化错误出现后立即发送简短状态通知，说明哪一步完成、哪一步被验证阻断，并交给现有宿主登录恢复流程；不要再走完整最终总结与重复改写。可以使用经过审核的状态文本，必要的人设化仅一次轻量调用并设置短时限。

本次失败通知延迟约 61 秒。应将“识别结构化错误到首次通知送达”设为独立指标，建议验收目标不超过 5–10 秒；这是目标，不是已有能力。461 的可用性问题需要验证恢复，增加下载速度或盲目并发上游 API 不能解决。

### 4. 图片下载并发与其他微调（次优先级）

`jobConcurrency=2` 是两个后台任务并发；单个 `downloadImages` 任务内部仍逐图 `await` 下载。可在受控预算内增加 2–4 个 CDN 下载并发，并保证共享预算、取消、失败清理和完整图集提交正确。但本次整个下载只花 3.910 秒，估计收益仅约 1–2 秒，远小于减少模型往返。

XHS 前台仍保留账号级限流与 FIFO，不建议为了提速直接并行搜索/详情。QQ 合并上传实测 9.712 秒，本地发送准备只约 0.38 秒；已合为一条转发消息，不宜为提速丢图或牺牲既定完整图集要求。

入站消息合并窗口当前约 1.5 秒，也可微调，但最多是约 1 秒量级收益，并会影响多段消息聚合，优先级低。

## 复现与记录

本轮仅添加/完善隔离测试计时与报告工具，未修改生产搜索/下载/投递策略，也未为本轮测试重启生产服务。

- `scripts/accept-xhs-live.mjs`：可选 `XHS_ACCEPT_TIMING=1`，记录入站与 QQ 请求/回执时间。
- `scripts/xhs-timing-preload.mjs`：只在隔离验收根目录启用，记录阶段类型和耗时，不记录 URL、body、header、token 或媒体路径；Node 20 凭据子进程跳过插桩。
- `scripts/report-xhs-timing.mjs`：只读聚合两个测试根目录，输出脱敏 JSON；区分工具执行成功、嵌套业务错误与实际媒体回执。
- `docs/XHS-PIPELINE-TIMING-20261022.json`：本次两份机器可读结果，含逐工具和逐模型调用时间，未包含账号、消息内容、帖子 URL、回执标识或凭据。

生成脱敏报告（只读，不访问小红书、不发 QQ）：

```bash
node scripts/report-xhs-timing.mjs \
  /root/.openclaw/state/xhs-integration-20261021/live-timing-20261022-1 \
  /root/.openclaw/state/xhs-integration-20261021/live-timing-20261022-2
```

3 个脚本通过语法检查；报告已核对正常/挑战两类结果、逐阶段时间、完整图集数量、真实发送回执与敏感字段排除。两次独立网关已退出，生产 `openclaw-gateway.service` 仍处于 active/running。
